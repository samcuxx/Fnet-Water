# F Net Water Hub — Architecture

This document describes the technical architecture of the F Net Water Hub web application.

The approved functional scope lives in [`FNET_WATER_HUB_REQUIREMENTS.md`](./FNET_WATER_HUB_REQUIREMENTS.md) and remains the source of truth. This document explains *how* that scope is implemented.

### Next.js 16 conventions that this codebase depends on

The bundled, version-matched docs in `node_modules/next/dist/docs/` are authoritative. The following v16 behaviours shape the code and differ from older Next.js:

- **Request APIs are async.** `cookies()`, `headers()`, `draftMode()`, and the `params` / `searchParams` props are Promises and must be awaited.
- **`proxy.ts` replaces `middleware.ts`.** The exported function is named `proxy`, and it always runs on the Node.js runtime (the `runtime` segment config is rejected in this file).
- **Typegen-provided prop helpers.** `PageProps<'/route'>`, `LayoutProps<'/route'>`, and `RouteContext<'/api/route'>` are globally available types generated by `next dev` / `next build` / `next typegen`. We use them instead of hand-written prop types.
- **Turbopack is the default** for `next dev` and `next build`.
- **`next lint` is removed.** Linting runs through the ESLint CLI with flat config (`eslint.config.mjs`).
- **Route Handler `GET` is dynamic by default.**
- **`error.tsx` receives `retry`** (stable in 16.3) and must be a Client Component.
- **Auth interrupts.** `forbidden()` and `unauthorized()` require `experimental.authInterrupts: true`, which we enable, together with `forbidden.tsx` / `unauthorized.tsx` UI files.

Cache Components (`cacheComponents: true`) are deliberately **not** enabled. This is an authenticated, per-user operational system where almost every page reads request-scoped session data, so the prerendering model would add migration cost without meaningful benefit.

### Prisma 7 conventions that this codebase depends on

Prisma 7 is a Rust-free rewrite and its project layout differs sharply from Prisma 5/6:

- **The `prisma-client` generator is the default** and `output` is **required**. The client is generated into the project source tree at `lib/generated/prisma`, not into `node_modules`. Imports are therefore `@/lib/generated/prisma/client`, never `@prisma/client`.
- **`prisma.config.ts` at the repo root** is the configuration entry point. The connection URL, schema path, migrations path, and seed command live there. `datasource.url` is no longer read from `schema.prisma`.
- **A driver adapter is required.** PostgreSQL uses `@prisma/adapter-pg`; the client is constructed as `new PrismaClient({ adapter })`.
- **No `postinstall` generation hook.** `prisma generate` must be invoked explicitly, so it is wired into the `postinstall` and `build` scripts in `package.json`.
- The generated directory is git-ignored and excluded from linting; it is a build artifact.

## 2. Layered architecture

Request flow, from the outside in:

```
Browser (desktop / tablet / mobile)
        │
        ▼
proxy.ts ──────────── optimistic, cookie-only session check + route gating
        │
        ▼
app/**  ───────────── routes, layouts, Server Components (presentation only)
        │
        ├─ Server Actions (app/**/actions.ts)   ┐
        └─ Route Handlers (app/api/**/route.ts) ┘ transport + input validation
        │
        ▼
lib/auth ─────────── session resolution, authorization gate (the DAL)
        │
        ▼
services/** ───────── business rules, invariants, database transactions
        │
        ▼
lib/db (Prisma) ──── PostgreSQL
        │
        └─ lib/storage (MinIO) for binary objects
```

### Rules of the layering

1. **React components never contain business rules.** A component may format, lay out, and branch on already-computed values. Deciding whether a bottle shortage becomes a charge, whether a status transition is legal, or whether ownership may transfer belongs in `services/`.
2. **Every entry point re-authorizes.** Server Actions and Route Handlers are independently reachable HTTP endpoints. Neither the proxy nor a parent layout is treated as a security boundary. The data-security guidance in the bundled docs is explicit about this, and the layout doc notes that layouts do not re-render on navigation and do not prevent nested segments from rendering.
3. **Services own transactions.** A service function is the unit of atomicity. Callers do not compose their own multi-step writes.
4. **Services are transport-agnostic.** They accept plain arguments and an actor context, never `Request`, `FormData`, or `NextResponse`. This is what makes the Phase 2 mobile app able to reuse them through Route Handlers.
5. **`import 'server-only'`** guards every module that touches secrets, the database, or session material.

## 4. Authentication

**Strategy: database-backed sessions with a signed, HTTP-only cookie.**

A stateless JWT alone cannot satisfy the requirement for account activation/deactivation, because a deactivated user would keep a valid token until expiry. Instead:

1. Credentials are verified against `users.password_hash` (bcrypt, cost 12). Passwords are never stored or logged in plaintext.
2. A `Session` row is created holding a **SHA-256 hash** of a 256-bit random session token, plus expiry, IP, and user agent. The raw token is never persisted, so a database leak does not yield usable sessions.
3. The raw token is wrapped in a JWT (`jose`, HS256) and written to an `httpOnly`, `sameSite=lax`, `path=/`, `secure`-in-production cookie.
4. On each request the DAL verifies the JWT signature, looks up the session by token hash, and confirms it is unexpired, unrevoked, and attached to an `ACTIVE` user.

Logout revokes the session row and clears the cookie, so the credential is dead server-side rather than merely forgotten by the browser.

### Session resolution and caching

`lib/auth/dal.ts` exposes:

- `getSession()` — returns the actor or `null`. Wrapped in React `cache()` so repeated calls within one render pass hit the database once.
- `requireSession()` — returns the actor or calls `unauthorized()`.
- `requireRole(...roles)` / `requirePermission(permission)` — returns the actor or calls `forbidden()`.

Registration is open only for the customer role. Staff accounts (administrator, manager, agent, driver) are created by an administrator, which matches the requirement that staff accounts are managed by authorized administrative users.

### The proxy is an optimization, not a gate

`proxy.ts` performs an *optimistic* check: it reads and verifies the cookie's signature and redirects unauthenticated visitors away from role prefixes, and signed-in users away from the auth pages. It does **no** database work, because the proxy runs on every request including prefetches.

The bundled proxy docs warn that Server Functions are handled as POSTs to the route where they are used, so a matcher change can silently remove proxy coverage. Authorization is therefore always repeated inside the DAL, next to the data.

## 5. Authorization (RBAC)

Roles are a fixed enum: `ADMINISTRATOR`, `MANAGER`, `AGENT`, `DRIVER`, `CUSTOMER`.

Authorization has two independent parts, and both are enforced server-side.

### 5.1 Capability check — "may this role do this kind of thing?"

`lib/permissions` defines granular permission strings (`order:cancel:any`, `inventory:adjust`, `payment:reverse`, `dispenser:transfer-ownership`, …) and a static matrix mapping each role to its permission set. Guards resolve a permission against the actor's role.

### 5.2 Ownership / scope check — "may this actor touch *this* record?"

A capability alone is not sufficient, since a customer holding `order:read:own` must not read another customer's order. Every service that loads a record by ID also asserts scope:

| Role | Scope rule |
| --- | --- |
| Customer | Records whose `customerId` equals the actor's own customer profile. |
| Driver | Deliveries assigned to the actor, and the customer/order data needed to complete them. |
| Agent | Customers the agent registered or referred, and orders belonging to those customers. |
| Manager | Operational records org-wide; sensitive financial and inventory corrections are limited to those the requirements permit. |
| Administrator | Full authorized access. |

This defeats the IDOR class of bug that a role-only check leaves open. The permission matrix in full, including the sensitive operations that require administrator authorization, is tabulated in [`BUSINESS_RULES.md`](./BUSINESS_RULES.md).

### 5.3 Interrupts

Missing session → `unauthorized()` → `app/unauthorized.tsx` (HTTP 401).
Present session, insufficient rights → `forbidden()` → `app/forbidden.tsx` (HTTP 403).

Both require `experimental.authInterrupts: true`. Because the bundled docs note that `try/catch` swallows these interrupts, service code that wraps calls in `try/catch` must re-throw via `unstable_rethrow`.

## 6. Money and quantities

**No floating point touches money.** Every monetary column is `Decimal(14, 2)` in PostgreSQL and `Prisma.Decimal` in TypeScript; arithmetic goes through `lib/money` helpers. Amounts cross the Server/Client boundary as strings and are rendered with `Intl.NumberFormat` for `GHS`.

Bottle counts are integers. A negative stock position is rejected at the service layer rather than being clamped, so a bug surfaces as a failed operation instead of silently corrupted inventory.

---

## 7. The inventory ledger

Stock is **derived from an append-only ledger**, not from an editable counter. This is the requirement's central accountability guarantee.

- `InventoryMovement` is append-only: no updates, no deletes. Each row records the movement type, quantity, source state, destination state, the actor, the linked order/delivery/customer/driver, and a reason.
- `BottleStockPosition` is a materialized quantity per `(state, driverId, customerId)`. It exists so that reads are cheap and so that concurrent writers have a single row to lock.

Every stock-changing operation, inside one transaction: locks the affected position rows, appends the movement, and applies the delta. A reconciliation report re-aggregates the ledger and compares it against the positions, so drift is detectable rather than invisible.

Bottle states: `FILLED_WAREHOUSE`, `EMPTY_WAREHOUSE`, `ASSIGNED_TO_DRIVER`, `IN_TRANSIT`, `WITH_CUSTOMER`, `DAMAGED`, `LOST`, `UNDER_INVESTIGATION`.

Drivers record operational events only. Manual quantity corrections require the `inventory:adjust` permission, always create an `InventoryAdjustment` row carrying previous quantity, new quantity, reason, and actor, and always write an `AuditLog` entry.

---

## 8. Financial integrity

Completed financial records are never deleted or edited in place.

`Payment` is the intent-and-outcome record. `PaymentTransaction` is the append-only ledger beneath it, with types `PAYMENT`, `REVERSAL`, `REFUND`, and `ADJUSTMENT`. A correction appends a compensating transaction; the original stays queryable, and a payment's effective amount is the sum of its transactions.

Reversals and refunds are therefore modelled as ledger entries rather than as separate tables. This is a deliberate normalization of the `Refund` entity named in the requirements — one ledger keeps the audit trail linear and makes "what is this payment actually worth now?" a single aggregate.

## 9. Concurrency

Concurrent requests could otherwise double-spend a reward, oversell stock, or pay an installment twice. Defences, in order of preference:

1. **Unique constraints** where the invariant is expressible as one: one qualified referral per referred customer, one reward redemption per order, unique payment references, unique idempotency keys on provider callbacks.
2. **Row locks inside transactions** (`SELECT … FOR UPDATE` via `$queryRaw`) on the specific contended row — the stock position, the reward balance, the installment plan — before reading-then-writing it.
3. **Guarded status transitions.** Conditional updates assert the expected current status in the `WHERE` clause, so a losing racer updates zero rows and fails loudly instead of overwriting.
4. **`Serializable` isolation** for the few flows where a phantom read would corrupt a balance.

The operations that must run in a transaction are enumerated in [`BUSINESS_RULES.md`](./BUSINESS_RULES.md) §Transactions.

## 10. Provider abstractions

### Payments

`lib/payments` defines a `PaymentProvider` interface (`initiate`, `verify`, `refund`, `parseWebhook`) with a registry keyed by `PAYMENT_PROVIDER`. Shipped drivers:

- `manual` — records cash, bank transfer, and staff-confirmed mobile money. Fully functional; no third-party dependency.
- A gateway driver placeholder that **throws a clear "not configured" error** rather than pretending to succeed.

Cash-on-delivery is a first-class flow: the driver records the amount collected, the transaction stores who collected it and when, and management reconciles it later. Drivers cannot edit historical payment records.

### Notifications

`lib/notifications` defines a `NotificationChannel` interface. Only the `in-app` channel is implemented in Phase 1, writing to the `Notification` table. SMS, WhatsApp, email, and push are registered but disabled, because those services carry per-message charges that §31 of the requirements excludes from Phase 1 cost. Enabling one is a configuration change, not a refactor.

### Smart dispenser tracking

No IoT hardware exists in Phase 1. The schema (`TrackerDevice`, `TrackerReading`, `TrackerAlert`) and the management UI are built so a future integration only needs an ingestion endpoint. Seeded tracker rows carry `isSimulated = true` and the UI labels them as demonstration data. Nothing claims a live device connection.

## 11. Object storage

Binary files live in MinIO; PostgreSQL stores only metadata and the object key (`StoredFile`).

Buckets are **private**. Reads go through either an authorized Route Handler that streams the object after a permission check, or a short-lived presigned URL. Uploads are validated for content type and size before the object is accepted, and the stored object name is a generated key rather than the user-supplied filename.

---

## 12. Reporting

Reports are server-rendered with mandatory bounds: a required date range, server-side pagination, and aggregate queries pushed into SQL (`groupBy` / `aggregate`) rather than fetching rows and summing in JavaScript. Indexes exist for the report filter columns listed in [`DATABASE.md`](./DATABASE.md).

---

## 13. Validation and error handling

Zod schemas in `lib/validation` are the single definition of a payload's shape and are used by both Server Actions and Route Handlers. Client-side validation exists for feedback only and is never trusted.

Services throw typed domain errors (`ValidationError`, `NotFoundError`, `ForbiddenError`, `ConflictError`, `BusinessRuleError`). The transport layer maps them to user-readable messages and appropriate HTTP status codes. Raw Prisma errors, stack traces, and connection strings never reach a client response; unexpected failures are logged server-side with a correlation id and surfaced generically.

---

## 14. Design system

Brand tokens are declared once in `app/globals.css` using Tailwind v4's `@theme` block: primary `#0057B8`, light `#00AEEF`, white `#FFFFFF`, plus semantic success/warning/danger scales and neutral greys.

Every role portal composes the same primitives, so the customer, driver, agent, manager, and administrator interfaces are visibly one product. Layout is mobile-first; the driver portal in particular is designed for a phone browser held one-handed, with large tap targets and a single-column task flow.

---

## 15. Testing

Vitest covers the business logic where a defect costs money or trust: order totals, bottle exchange accounting, shortage recording, inventory movements, delivery completion, failed-delivery reconciliation, installment schedules and balances, payment recording and reversal, referral qualification, and reward earning and redemption. Permission-matrix tests assert that each role is denied what it must not reach.

---

## 16. Deployment

Docker Compose runs `app`, `postgres`, and `minio` on one network with named volumes for the database and object data, so state survives container restarts. Health checks gate startup ordering. The production image is a multi-stage build producing Next.js `standalone` output and runs as a non-root user. Secrets come from the environment; none are committed.
