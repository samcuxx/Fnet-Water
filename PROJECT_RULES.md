# F NET WATER HUB — ENGINEERING RULES & QUALITY CONTRACT

This document defines the strict, non-negotiable operational rules for the engineering and development of **F Net Water Hub**. Every code change, component migration, state structure, and user interface element must comply with these guidelines.

---

## 1. TECH STACK SPECIFICATION

The production tech stack is strictly defined as follows:

- **Framework**: **Next.js** (App Router, TypeScript, React 19)
- **Database**: **PostgreSQL 16** (Docker container locally & in production)
- **ORM & Data Layer**: **Prisma ORM** (type-safe queries, migrations, seeders)
- **Styling & UI**: **Tailwind CSS v4** + TailAdmin React v2.3.0 components (`ui_template`)
- **Authentication**: **NextAuth.js / Auth.js** (Credentials Provider with role-based JWT sessions & mNotify OTP verification)
- **Payment Gateway**: **Paystack** (Ghana Mobile Money: MTN, Telecel, AirtelTigo, Cards, Bank Transfer + Webhook automation)
- **SMS & OTP Provider**: **mNotify Ghana** (`https://api.mnotify.com/api/sms/quick`)
  - Sender ID: `Fnet`
  - Project: `Fnet`
- **Containerization & DevOps**: **Docker** (Multi-stage standalone build) + **Docker Compose**
- **Production Hosting Target**: Self-hosted via **Coolify** (developed locally via Docker first)

## 2. ANTI-SLOP & PROFESSIONAL CRAFTSMANSHIP RULES

Following the principles of the **Anti-Slop Standard** (`https://github.com/miqdadbadjuber/anti-slop`), all output must feel designed by a focused human engineer, never generated by an unconstrained AI.

### Rule 2.1: No AI Copywriting Slop & Word Bans
- **FORBIDDEN VOCABULARY**: Never use AI buzzwords or abstract inflation words:
  - *Banned*: `unlock`, `elevate`, `empower`, `seamless`, `cutting-edge`, `revolutionary`, `robust`, `delve`, `game-changer`, `next-level`, `testament`, `usher in`, `pivotal`, `groundbreaking`.
- **FORBIDDEN CHARACTER**: Never use the em dash (`—`) in UI copy or descriptions. Use commas, periods, colons, or parentheses instead.
- **Direct, Human Sentences**: Write clear, plain statements. State what the software does without fluff.
  - *Bad*: "Unlock the power of revolutionary water management with our cutting-edge platform."
  - *Good*: "Order water refills, schedule bulk deliveries, and manage dispenser plans."

### Rule 2.2: No Cluttered or Bombarded Card Grids
- **Never Bombard the Screen**: Avoid multi-paragraph cards, redundant badges, and wall-to-wall card grids where simple lists, clean tables, or quiet layouts belong.
- **Card Discipline**: A card must hold real, actionable operational data (such as a metric, an order summary, or an address record). Cards are never used as decorative text blocks.
- **Keep Descriptions Minimal**: If a card has a title and an action button, do not write a paragraph explaining what the button does.

### Rule 2.3: Unified Brand Logo Standard (No Random Placeholders)
- **Single Logo Throughout**: Never generate temporary letters in gradient boxes (e.g. an "F" in a square).
- Always use the official F Net Water Hub logo component:
  - Component: `src/components/brand/Logo.tsx` (`<Logo />` or `<LogoIcon />`)
  - Static SVG assets: `public/images/logo/logo.svg`, `logo-dark.svg`, and `logo-icon.svg`.

### Rule 2.4: Restrained Visual Hierarchy (No Trend Stacking)
- **No Trend-Stacking**: Never combine glassmorphism + glow + pulsing dot + pill badges + gradient borders simultaneously.
- **Solid, Clean Surfaces**: Match TailAdmin React aesthetics:
  - Clean white cards (`bg-white dark:bg-gray-900`)
  - Subtle borders (`border-gray-200 dark:border-gray-800`)
  - High-contrast text (`text-gray-900 dark:text-white`)
  - Primary CTA in official Brand Blue (`#0057B8`)
  - Subtle cyan accents (`#00AEEF`)
- **No Pulse Dots Without Hardware**: Do not add blinking green/red dots to simulate status unless it represents live IoT sensor data.

### Rule 2.5: Craftsmanship Principles (C-1 to C-5)
1. **C-1 Intentionality**: Every visual decision must have a concrete reason. If it's an AI default, remove it.
2. **C-2 Functional Completeness**: Every button and link must have a working destination. No dead controls.
3. **C-3 Content-Driven**: Content dictates the layout, not an arbitrary AI template.
4. **C-4 Resilience**: Complete UI states for empty data, loading, and errors.
5. **C-5 Evidence Over Claims**: Display only real numbers and verifiable facts. No fake claims or fake stats.

## 3. TECHNICAL & OPERATIONAL RULES

### Rule 3.1: Zero Blind Coding
- Always inspect existing files in `ui_template` before referencing or porting them to Next.js.
- Verify imported dependencies and types before using them.
- Any shell command must be run with deliberate parameters (e.g. `npm.cmd` on Windows to avoid execution policy errors).

### Rule 3.2: Absolute UI Template Fidelity in Next.js
- Every UI component, layout pattern, modal, badge, button, form element, table, card, chart, and icon must originate exclusively from the `ui_template` codebase.
- Components utilizing React hooks (`useState`, `useEffect`, `useContext`, `usePathname`), event handlers, or browser APIs must declare `'use client'` at the top.
- Components requiring browser-only libraries (`react-apexcharts`, `flatpickr`) must be imported dynamically with `ssr: false` to prevent hydration mismatches.

### Rule 3.3: Database & Prisma ORM Integrity
- All persistent data must be modeled in `prisma/schema.prisma`.
- Always use typed Prisma queries.
- Database migrations and seed scripts must populate realistic Ghanaian water business data.

### Rule 3.4: Paystack Payment & Security Rules
- `PAYSTACK_SECRET_KEY` must strictly reside on the server and must **never** be exposed in client bundles.
- The Paystack webhook route (`/api/webhooks/paystack`) must verify the `x-paystack-signature` header using HMAC SHA512 before processing any event.
- All payment callbacks must be idempotent.

### Rule 3.5: mNotify SMS & OTP Rules
- Centralized helper in `src/lib/mnotify.ts` to dispatch transactional messages.
- Phone numbers normalized to standard Ghanaian format (`024XXXXXXX` or `23324XXXXXXX`).
- Graceful error handling so SMS delivery issues never crash calling functions.

## 4. DUAL TESTING PROTOCOL

### Stage 1: AI Developer Self-Verification (Mandatory Before Handover)
1. **Type Safety & Build Verification**:
   Execute `npx.cmd tsc --noEmit` and `npm.cmd run build`. Ensure zero TypeScript compilation errors and clean bundle.
2. **Database Integrity**:
   Verify Prisma Client generation and schema validity.
3. **Responsive Verification**:
   Ensure layouts adapt cleanly across desktop (`1280px+`), tablet (`768px - 1024px`), and mobile (`< 640px`) without overflow.

### Stage 2: User Acceptance Testing (UAT) Handover
Every completed module report must conclude with a structured **Reviewer Testing Guide** containing:
- **Test Persona**: Role to test as
- **Credentials / Access**: How to access the view
- **Step-by-Step Test Scenario**: Clear 1-2-3 actions
- **Expected Outcome**: What the user should see in the UI.
